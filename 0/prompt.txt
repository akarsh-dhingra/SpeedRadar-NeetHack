## 2. The product

**One-liner:** An agent that tells a finance team where competitors are outspending them, and shows its work — every number has a source, and the agent tries to disprove its own findings before reporting them.

**Problem:** Finance teams budget against their own ledger, not the market. They learn a competitor doubled its ML team or raised a round a quarter late.

**The task the agent completes end to end:**
> Input: a folder of the company's finance files (budget spreadsheet, invoice PDFs, vendor contracts, a spend policy) and a list of 3–5 competitors (or let the agent pick them).
> Output: a report per spend category (engineering, ML/AI, sales, marketing, infra/cloud) with our actual spend, the competitor estimate range, the gap, whether policy is violated, a recommendation, and a link to every source behind every number — plus a list of claims the agent checked and overturned.

**Positioning for these judges:** use a dev-tools / AI-infra fictional company ("Acme Observability Inc." — clearly labelled fictional) and real dev-tools / AI-infra competitors, so the judges recognise the market.

## 4. Agent architecture

### 4.1 The loop (not a fixed pipeline)

```
PLAN → ACT → OBSERVE → VERIFY ─┬─ pass → next task
                               └─ fail → add fix-up task → ACT
when queue empty → SELF-AUDIT → REPORT
```

1. **Plan**: LLM reads the goal, file listing, and competitor list; writes a task queue into state (which files to parse, which competitors to fetch, which categories to compare). The plan is a traced span.
2. **Act**: pick the next task, call exactly one tool.
3. **Observe**: store the result in state *with its source* (file path + sheet/row or page; Crustdata endpoint + request id + timestamp).
4. **Verify**: run the deterministic check for that result type (§4.4). On failure, push a fix-up task (re-parse with the other parser, narrow page range, fetch an extra signal, mark low-confidence) and loop. Cap retries per task at 3.
5. **Self-audit** (key differentiator): after all findings exist, a second pass tries to *disprove* each finding — re-checks its sources, searches for a contradicting signal (e.g. a hiring freeze or layoffs post), recomputes the number. Findings that fail are downgraded or removed and logged as "overturned".
6. **Report**: write `runs/<run_id>/report.md` (and `report.html`) with every number linked to its source and an "Overturned claims" section.

### 4.2 Tools (functions the agent can call)

| Tool | Deterministic? | Purpose |
|---|---|---|
| `list_files(folder)` | yes | inventory inputs |
| `read_spreadsheet(path, sheet, range)` | yes | budget lines |
| `read_pdf(path, pages, mode="text"/"llm")` | text: yes; llm: no | invoices, contracts |
| `crustdata_company(name_or_domain)` | yes (API) | headcount, funding, basic info |
| `crustdata_jobs(company, filters)` | yes (API) | open roles; aggregate by team if supported |
| `classify_titles(titles)` | no (LLM) | map job titles → spend category (fallback if no team breakdown) |
| `estimate_spend(headcount_by_category, salary_table)` | yes | headcount → estimated annual spend |
| `compare(ours, theirs, policy)` | yes | gap + policy violation per category |
| `find_contradictions(finding)` | mixed | used by self-audit |
| `write_report(state)` | yes | final output |

All money/maths is deterministic Python. The LLM plans, classifies, interprets, and writes prose — it never does arithmetic that ends up in the report.

### 4.3 State and resumability

- One `RunState` (Pydantic) per run: goal, task queue, completed tasks, extracted figures (value + source), competitor figures (value + source), verification results, retry counts, overturned findings, token/cost totals.
- Save to `runs/<run_id>/state.json` after **every** step. `python -m spendradar resume <run_id>` continues from the last saved step. Demo this.
- Cache every Crustdata response to `cache/crustdata/<hash>.json`; never re-spend credits in test runs.

### 4.4 Verification checks (confidence is computed from these, never typed in)

- Spreadsheet/invoice line items sum to the stated total within 1%.
- Each invoice amount appears in the budget category it is mapped to (or is flagged).
- Each competitor estimate rests on ≥ 2 independent signals, else `low_confidence`.
- Every number in the report has a stored source; a number without one is dropped.
- `confidence = f(checks passed, number of signals, data freshness)` — implement in `verify.py`, document the formula in the README.

### 4.5 Recovery paths (each must appear in at least one saved trace)

- Corrupt/unreadable PDF → try other parser → skip and list under "Not analysed".
- Crustdata timeout / rate limit / 5xx → exponential backoff, max 3 retries → cached response if available → mark data missing.
- Competitor with no data → substitute next-closest company, note it in the report.
- Totals mismatch → re-read with narrower range → flag the file.
- LLM returns malformed JSON → re-ask with the validation error, max 2 times.

Q4: Yes to your proposal, with one addition.

Competitor side: the first pass builds each finding from one signal, and the audit checks it against independent signals. A disagreement counts as an overturn, but the eval doesn’t call it right or wrong. The report should show both sources side by side so the reader can judge.
Scored metric: runs on the planted internal errors in ground_truth.json (bad totals, the mis-categorised invoice, the corrupt file).
Addition, fault injection on the competitor side. In evals/fixtures/, take a few cached real Crustdata responses and change one field on purpose, for example inflating ML job postings 5×.
